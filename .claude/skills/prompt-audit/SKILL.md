# 프롬프트 평가

클로드 코드가 남긴 대화 기록(`~/.claude/projects/**/*.jsonl`)을 읽어, 사람이
입력한 프롬프트를 두 가지 기준으로 채점한다. 하나는 문장 자체의 품질이고, 다른
하나는 그 문장이 실제로 만들어 낸 결과의 품질이다. 둘 다 100점 만점이다.

## 실행 순서

### 1. 무엇을 분석할지 묻는다

먼저 컴퓨터에 남아 있는 대화 기록을 훑어, 분석할 수 있는 대상 목록을 뽑는다.

```bash
cd C:/dev/weekly_project && PYTHONPATH=src python -m promptaudit --list
```

아래처럼 표가 나온다. 기록이 많으면 1~2분 걸린다.

```
  번호  이름                            세션   프롬프트   기간
    1.  ReviewTicketFullstack             28      1600   2026-07-28 ~ 2026-08-26
    2.  MyCloset                          13       561   2026-07-26 ~ 2026-08-20
```

이 표를 그대로 사용자에게 보여 주고 **무엇을 분석할지 물어본다.** 그리고 이어서
**최종 리포트 html을 어디에 만들지도 물어본다.** 사용자가 폴더만 말하면 그 안에
`report.html` 로 만들고, 파일 이름까지 말하면 그 이름을 그대로 쓴다. 아무 말이
없으면 프로젝트 폴더 안의 `out/report.html` 이 기본이다.

두 가지를 다 받은 뒤에 실행한다.

```bash
cd C:/dev/weekly_project && PYTHONPATH=src python -m promptaudit --project ReviewTicketFullstack --html "C:/Users/bryan/OneDrive/바탕 화면/report.html"
```

옵션 없이 그냥 실행하면 프로그램이 터미널에서 사람의 입력을 기다린다. 사람이
직접 명령을 칠 때는 그 편이 편하지만, 이 스킬이 대신 실행할 때는 입력을 넣을 수
없어 멈춰 버린다. **그러므로 스킬은 반드시 `--project`를 붙여 실행한다.**

만들어지는 파일은 다음과 같다.

| 파일 | 내용 |
| --- | --- |
| `out/report.html` | 네 개 장으로 나뉜 리포트. 위쪽 버튼으로 이동한다. `--html`을 주면 그 자리에도 똑같이 하나 더 만든다 |
| `out/report.md` | 같은 내용의 마크다운 |
| `out/charts/*.png` | 발표 슬라이드에 붙일 그림 |
| `out/scores.json` | 프롬프트별 점수와 채점 기준 원본 |
| `out/judge_queue.json` | 아직 채점하지 않은 프롬프트 대기열 |

규칙만으로도 리포트가 완성되므로 여기서 끝내도 된다. 채점을 아예 반영하고 싶지
않으면 `--no-llm`을 붙인다.

### 2. 대기열을 채점한다

`out/judge_queue.json`을 읽는다. 파일 안의 `instructions` 필드에 채점 방법이
들어 있다. 각 항목을 **두 번** 채점한다.

- **blind** - `prompt` 필드만 읽는다. `what_happened` 필드는 절대 보지 않는다.
- **aware** - `prompt`와 `what_happened`를 모두 읽고 다시 매긴다.

여섯 축은 목표 명확성, 컨텍스트 충분성, 제약과 범위, 검증 기준, 작업 분해,
재사용성이며 각각 1~5점이다. 두 점수의 차이가 "문장은 멀쩡했는데 결과가 안
따라온" 프롬프트를 드러내므로, blind 채점에서 결과를 미리 보지 않는 것이 이
시스템의 핵심이다.

결과는 `out/judge_results.json`에 아래 형태로 쓴다.

```json
{
  "<항목 id>": {
    "blind": {"goal_clarity": 3, "context": 2, "scope": 2,
              "verification": 1, "decomposition": 4, "reusability": 2},
    "aware": {"goal_clarity": 2, "context": 1, "scope": 2,
              "verification": 1, "decomposition": 3, "reusability": 1},
    "verdict": "무엇이 문제였는지 한 문장",
    "rewrite": "같은 의도를 더 잘 전달하는 프롬프트 재작성본"
  }
}
```

한 번에 전부 채점할 필요는 없다. 일부만 채점해도 리포트에 반영되고, 이미 채점한
항목은 `out/judge_cache.json`에 쌓여 다음에 다시 묻지 않는다. `rewrite`에 적은
문장은 리포트 3장의 "이렇게 다시 써 보세요"에 그대로 실린다.

### 3. 채점을 반영해 다시 만든다

같은 명령을 다시 돌리면 채점 결과가 병합되어 리포트에 반영된다.

## 리포트 구성

| 장 | 내용 |
| --- | --- |
| 1장. 평가 지표 | 요약 수치와 그림 여섯 장 |
| 2장. 상세 분석 | 잘 쓴 프롬프트, 못 쓴 프롬프트, Claude의 문제. 펼치면 원문 전체가 보인다 |
| 3장. Feedback | 기준선을 넘긴 항목에 대한 구체적인 개선 지시와 재작성 예시 |
| 4장. 채점 기준 | 100점을 어떻게 나눠 매기는지와 항목별 획득 점수 |

2장의 "Claude의 문제"는 사람이 문장을 잘 썼는데도 결과가 따라오지 않은 경우를
모아 둔 자리다. 프롬프트를 더 다듬어서 해결되는 문제가 아니므로 따로 구분한다.

## 주의할 점

- 인용되는 프롬프트 원문은 마스킹을 거치지만, 발표 자료로 옮기기 전에 눈으로 한
  번 더 확인한다.
- 결과 점수에는 과제 난이도라는 교란 변수가 있다. 상관을 인과로 읽지 않는다.
- 기록 파일은 UTF-8이다. PowerShell `Get-Content`로 직접 열면 한글이 깨진다.
