# 기획서 - 클로드 코드 프롬프트 분석 시스템

## 1. 배경

5주차 주제는 "AI와의 협업 과정을 돌아보고 개선할 수 있는가"이다. 이 질문에
답하려면 우리가 실제로 AI에게 무엇을 어떻게 시켰는지에 대한 기록이 있어야
한다. 기억에 의존한 회고는 인상평이 되기 쉽다. "그때 프롬프트를 잘 썼던 것
같다"는 말에는 근거가 없다.

다행히 근거가 이미 남아 있다. 클로드 코드는 모든 대화를 사용자 홈 폴더 아래
`~/.claude/projects/**/*.jsonl` 경로에 JSONL로 기록한다. 이 파일에는 사람이
입력한 프롬프트 원문, 모델의 응답, 호출한 도구와 그 성패, 토큰 사용량,
타임스탬프, 사용자가 중간에 작업을 끊었는지 여부까지 들어 있다.

즉 우리는 이미 수천 건의 협업 기록을 가지고 있으면서 한 번도 그것을 들여다본
적이 없는 상태다. 이 시스템은 그 기록을 열어 보는 도구다.

## 2. 문제 정의

프롬프트 품질을 이야기할 때 흔히 문장만 본다. 구체적으로 썼는가, 맥락을
줬는가, 요구가 명확한가 같은 것들이다. 그러나 이 기준만으로는 중요한 질문이
빠진다. **그 프롬프트가 실제로 원하는 결과를 만들어 냈는가.**

문장이 잘 다듬어져 있어도 모델이 엉뚱한 파일을 고치거나, 열 턴을 더 쓰거나,
결국 사용자가 중간에 끊어 버렸다면 그 프롬프트는 좋은 프롬프트가 아니다.
반대로 "그거 다시 해 줘" 같은 부실한 문장이 앞 맥락 덕분에 정확히 통했을
수도 있다.

따라서 이 시스템은 프롬프트를 **입력 축**과 **결과 축** 두 개로 나누어
독립적으로 채점하고, 둘을 교차해 본다.

## 3. 목표

| 목표 | 판단 기준 |
| --- | --- |
| 협업 기록을 수치로 만든다 | 세션 선별부터 점수 산출까지 명령 한 줄로 재현된다 |
| 문장과 결과를 분리해 본다 | 프롬프트 점수와 결과 점수가 서로 다른 근거로 계산된다 |
| 읽을 수 있는 결론을 낸다 | 그래프, 해석, 조언이 순서대로 이어지는 리포트가 나온다 |
| 다음 행동을 제시한다 | 조언이 고정 문구가 아니라 이번 데이터의 임계값 초과 항목에서 나온다 |

## 4. 범위

분석 대상은 ReviewTicketFullstack 프로젝트 세션으로 한정한다. 세션 선별은 두
가지 근거의 합집합으로 한다.

- 세션 레코드의 작업 폴더가 `C:\dev\ReviewTicket...` 아래인 경우
- 데스크톱 앱에서 폴더를 열지 않아 작업 폴더가 바탕화면으로 남았지만, 사람이
  입력한 프롬프트 본문에 프로젝트 이름이 반복해 등장하는 경우

두 번째 조건이 필요한 이유는 실측에서 드러났다. 전체 레코드의 대다수가 작업
폴더를 바탕화면으로 기록하고 있어, 경로만 믿으면 실제 프로젝트 대화의 상당수를
놓친다.

## 5. 핵심 아이디어 - 두 축과 네 구역

프롬프트 점수를 가로축, 결과 점수를 세로축에 놓고 흩뿌리면 네 구역이 생긴다.
이 그림이 시스템의 중심이다.

| 구역 | 해석 |
| --- | --- |
| 프롬프트 좋음 + 결과 좋음 | 재현할 가치가 있는 패턴 |
| 프롬프트 좋음 + 결과 나쁨 | 문장 문제가 아니라 과제 자체가 어려웠던 경우 |
| 프롬프트 나쁨 + 결과 좋음 | 앞 맥락이 받쳐 준 경우, 새 세션에서는 재현되지 않는다 |
| 프롬프트 나쁨 + 결과 나쁨 | 명백한 안티패턴 |

특히 두 번째와 세 번째 구역이 이번 주제에 정면으로 답하는 소재다. 프롬프트를
다듬는 것만으로 해결되지 않는 지점이 어디인지 보여 주기 때문이다.

## 6. 결과 품질을 재는 방법

결과 축은 네 층으로 나누어 재고 가중 합산한다.

| 층 | 비중 | 무엇을 보는가 | 데이터 출처 |
| --- | --- | --- | --- |
| 즉시 성공 | 35% | 도구 실행이 에러 없이 끝났는가, 사용자가 끊지 않았는가 | `tool_result.is_error`, 중단 표시 |
| 수렴 비용 | 25% | 몇 턴, 몇 번의 도구 호출, 같은 파일 몇 번 재편집으로 끝났는가 | 응답 레코드와 Edit/Write 호출 |
| 지속성 | 20% | 그때 고친 파일이 실제 커밋까지 갔는가 | 프로젝트 저장소의 커밋 이력과 대조 |
| 사용자 수용 | 20% | 다음 프롬프트가 승인이었는가 정정이었는가 | 후속 프롬프트의 첫머리 표현 |

## 7. 채점 계층

규칙 기반 지표만으로는 "왜 나빴는지"를 말하기 어렵다. 그래서 표본 프롬프트에
대해 LLM 채점을 얹는다. 같은 프롬프트를 두 번 채점하는 것이 특징이다.

- **블라인드 채점** - 프롬프트 문장만 보여 주고 결과를 감춘다
- **결과 인지 채점** - 그 뒤에 실제로 벌어진 일까지 함께 보여 준다

두 점수의 차이가 곧 우리가 좋다고 착각했던 프롬프트의 목록이 된다.

채점 주체는 클로드 코드 자신이다. 시스템이 채점 대기열을 JSON으로 뽑아 두면
스킬이 그것을 읽어 채점 결과를 돌려준다. 별도의 API 키가 필요 없고, 과제 주제인
"클로드를 개발 업무에 활용한다"에도 그대로 부합한다.

## 9. 한계

결과 점수에는 과제 난이도라는 교란 변수가 섞여 있다. 어려운 작업일수록 턴이
늘고 에러가 잦지만 그것이 반드시 프롬프트 탓은 아니다. 따라서 두 점수의 상관을
인과로 읽어서는 안 되며, 이 리포트는 개선 지점을 찾는 출발점으로만 쓴다.

또한 분석 대상이 한 사람의 기록이므로, 팀 전체의 협업 습관으로 일반화하려면
팀원 각자의 트랜스크립트를 모아 같은 파이프라인에 넣어야 한다.
