# 5주차 과제 — 클로드 코드 프롬프트 분석 시스템

## Context

5주차 과제의 평가 질문은 "AI와의 협업 과정을 돌아보고 개선할 수 있는가"이며, 필수 내용은 프롬프트 분석, 잘못된 점, 잘 사용한 점, 보완점 네 가지다. 즉 프롬프트를 잘 쓰는 요령을 정리하는 과제가 아니라, 우리가 실제로 남긴 프롬프트 기록을 근거로 스스로를 진단하는 과제다.

다행히 근거 데이터가 이미 로컬에 쌓여 있다. Claude Code는 모든 대화를 `C:\Users\bryan\.claude\projects\C--Users-bryan-OneDrive------\*.jsonl`에 JSONL로 기록하며, 현재 119개 세션 564MB가 존재한다. 이 기록에는 사람이 입력한 프롬프트 원문, 모델의 응답, 도구 호출 내역, 토큰 사용량, 타임스탬프, 사용자 중단 여부가 전부 들어 있다. 따라서 "느낌상 이 프롬프트가 좋았다"가 아니라 측정된 수치로 프롬프트 품질을 논할 수 있다.

이번에 만들 시스템은 이 JSONL을 읽어 ReviewTicketFullstack 프로젝트 세션만 골라내고, 규칙 기반 지표로 정량화한 뒤 LLM 판정으로 해석을 붙여, 발표에 그대로 쓸 수 있는 HTML/Markdown 리포트를 뽑아 주는 슬래시 커맨드다.

## 확정된 설계 결정

| 항목 | 결정 |
| --- | --- |
| 산출물 형태 | Claude Code 스킬 `/prompt-audit` + Python 분석기 → HTML/MD 리포트 |
| 분석 엔진 | 규칙 기반 지표 + LLM 루브릭 판정 하이브리드 |
| 분석 대상 | ReviewTicketFullstack (구 ReviewTicket repo 포함) |
| 세션 선별 | cwd prefix 매칭 + 사람 프롬프트 본문 키워드 매칭의 합집합 |

## 대상 데이터 실측치

선별 규칙을 실제로 돌려 본 결과는 다음과 같다.

| 구분 | 수치 |
| --- | --- |
| 전체 세션 | 119개 (564MB) |
| 선별된 ReviewTicket 세션 | 30개 |
| 그 중 cwd만으로 잡히는 세션 | 22개 |
| 대화 내용으로만 잡히는 세션 | 8개 |
| 선별 세션의 사람 프롬프트 | 1,718개 |
| 전체 코퍼스의 사람 프롬프트 | 3,177개 |
| 사용자 중단 이벤트 (전체) | 198건 |

도구 호출 분포는 Bash 5,344, Read 2,198, Edit 1,512, PowerShell 1,215, Write 810, Grep 356 순이며, 이 분포 자체가 "탐색보다 실행에 치우친 협업 습관"이라는 발표 소재가 된다.

## 데이터 파싱 함정 (먼저 알고 시작할 것)

탐색 과정에서 실제로 걸렸던 함정들이다. 구현 시 이 네 가지를 처음부터 반영한다.

1. **인코딩** — PowerShell `Get-Content`는 기본 ANSI로 읽어 한글 프롬프트를 깨뜨리고 `ConvertFrom-Json`까지 실패시킨다. 파싱은 전부 Python `open(..., encoding='utf-8')`로 한다.

2. **`type: "user"`가 사람이 아니다** — 도구 실행 결과도 `user` 레코드로 들어온다. 전체 user 레코드 18,131개 중 사람이 친 것은 `origin.kind == "human"`인 3,433개뿐이다. 이 필터가 없으면 지표가 통째로 오염된다.

3. **MEMORY.md 주입으로 인한 키워드 오탐** — 세션마다 MEMORY.md가 컨텍스트로 주입되는데 그 안에 ReviewTicket 항목이 여러 개 있다. 레코드 전체를 대상으로 키워드를 찾으면 119개 중 74개가 걸려 사실상 무의미해진다. 키워드 스캔은 사람 프롬프트 본문에만, `<system-reminder>` 블록을 제외하고 적용해야 하며 그래야 30개로 좁혀진다.

4. **서브에이전트 혼입** — `isSidechain: true` 레코드는 서브에이전트 대화다. 사람이 쓴 프롬프트가 아니므로 본 지표에서 제외하고 별도 집계한다.

## 시스템 구조

```
/prompt-audit  (Claude Code 슬래시 커맨드)
      │
      ▼
[1] loader    : JSONL 스트리밍 파싱, 레코드 정규화
[2] selector  : cwd prefix + 본문 키워드로 ReviewTicket 세션 선별
[3] metrics   : 규칙 기반 정량 지표 산출 (LLM 미사용)
[4] rubric    : 샘플 프롬프트에 대해 LLM 6축 채점 + 재작성 예시
[5] report    : HTML + Markdown 동시 생성
```

3단계까지는 결정적이고 무료다. LLM은 4단계에만 개입하므로 재실행 비용이 낮고, 지표 수치는 몇 번을 돌려도 같은 값이 나와 발표 중 재현 시연이 가능하다.

## 규칙 기반 지표

프롬프트 하나마다 아래를 계산한다.

| 지표군 | 항목 |
| --- | --- |
| 형태 | 길이(문자/근사 토큰), 코드블록 포함, 파일 경로 언급, 첨부 유무 |
| 명확성 대용치 | 요청 동사 유무, 모호어 빈도("적당히", "알아서", "좀", "잘") |
| 제약 명시 | 금지·범위 한정 표현("~하지 마", "~만", "~빼고") 포함 여부 |
| 결과 반응 | 직후 어시스턴트 턴의 도구 호출 수, 출력 토큰, 응답 소요 시간 |
| 실패 신호 | 직후 사용자 중단 발생, 권한 거부 발생 |
| 재작업 신호 | 다음 프롬프트가 정정어로 시작("아니", "그게 아니라", "다시", "말고") |

세션 단위로는 턴 수, 총 토큰, 캐시 재사용률, 도구 분포, 재작업률을 집계한다.

## 결과물 품질 축 (프롬프트 점수와 분리해 따로 측정)

프롬프트를 문장만 보고 채점하면 "잘 쓴 것처럼 보이는 프롬프트"에 높은 점수가 가고, 정작 그 프롬프트가 무엇을 만들어 냈는지는 평가에서 빠진다. 좋은 프롬프트의 정의는 결국 "원하는 결과물을 적은 비용으로 얻어낸 프롬프트"이므로, 결과 쪽 점수를 독립적으로 계산해 프롬프트 점수와 나란히 놓는다. 결과 측정에 필요한 재료는 로그에 이미 다 있다.

| 층 | 측정 항목 | 데이터 출처 |
| --- | --- | --- |
| 즉시 성공 | 도구 실행 에러율, 첫 시도 성공 여부 | `tool_result.is_error` (전체 5.3%, 743/14,014) |
| 수렴 비용 | 목표 도달까지 걸린 턴 수, 소비 토큰, 같은 파일 재편집 횟수 | Edit/Write의 `file_path` 반복 카운트 (예: build.js 85회) |
| 지속성 | 그 세션이 건드린 파일이 실제 커밋까지 갔는지, 이후 되돌려졌는지 | 세션 중 `git commit` 호출 90건 + `C:\dev\ReviewTicketFullstack` 레포 커밋 248개 대조 |
| 사용자 수용 | 다음 프롬프트가 승인성인지("좋아", "됐다", "그대로 가") 정정성인지 | 후속 사람 프롬프트 분류 |

이 네 층을 합산해 프롬프트마다 결과 점수를 매긴다. **재작업률**(정정 프롬프트 비율), **중단률**, **도구 에러율**이 결과 축의 핵심 세 지표이고, "잘못된 점"을 주장할 때 이 수치에 걸린 실제 프롬프트 원문을 인용하면 근거가 선다.

### 두 축을 교차한 4분면 — 발표의 중심 그림

프롬프트 점수를 가로축, 결과 점수를 세로축에 놓고 1,718개 프롬프트를 흩뿌리면 네 구역이 나온다.

| 구역 | 해석 | 발표에서 쓰는 자리 |
| --- | --- | --- |
| 프롬프트 좋음 + 결과 좋음 | 재현할 가치가 있는 패턴 | 잘 사용한 점 |
| 프롬프트 좋음 + 결과 나쁨 | 프롬프트 탓이 아니라 과제 자체가 어려웠던 경우 | 한계 및 알게 된 점 |
| 프롬프트 나쁨 + 결과 좋음 | 이전 턴 컨텍스트나 운으로 넘어간 경우 | 협업 구조 얘기 |
| 프롬프트 나쁨 + 결과 나쁨 | 명백한 안티패턴 | 잘못된 점, 보완점 |

특히 두 번째와 세 번째 구역이 이번 과제의 평가 질문("협업 과정을 돌아보고 개선할 수 있는가")에 정면으로 답하는 소재다. 다만 결과 품질에는 과제 난이도라는 교란 변수가 있어 상관관계를 인과로 읽으면 안 되며, 이 한계는 리포트와 발표에 명시한다.

## LLM 판정 계층

전량 채점은 비용이 크므로 층화 표본을 쓴다. 재작업·중단 신호가 붙은 프롬프트 전량, 지표 상위·하위 구간, 무작위 표본을 합쳐 150~200개를 뽑는다.

채점은 같은 프롬프트에 대해 두 번 돌린다. 먼저 **블라인드 채점**은 프롬프트 문장만 보여 주고 결과를 감춘 채 매기고, **결과 인지 채점**은 그 뒤에 벌어진 일(도구 호출, 에러, 재편집, 사용자 반응)까지 붙여 주고 매긴다. 두 점수의 차이가 곧 "잘 쓴 줄 알았는데 실제로는 안 통한 프롬프트"의 목록이 되며, 이게 위 4분면의 두 번째·세 번째 구역을 채운다.

채점 축은 여섯 개이며 각 1~5점이다.

| 축 | 묻는 것 |
| --- | --- |
| 목표 명확성 | 무엇을 원하는지 한 번에 읽히는가 |
| 컨텍스트 충분성 | 파일·에러·현재 상태를 줬는가 |
| 제약과 범위 | 건드리면 안 되는 것을 명시했는가 |
| 검증 기준 | 완료 판단 기준을 제시했는가 |
| 작업 분해 | 한 프롬프트에 과하게 몰아넣지 않았는가 |
| 재사용성 | 규칙으로 승격시킬 만한 지시인가 |

출력은 JSON으로 받되 축별 점수, 근거 한 문장, 그리고 **개선 프롬프트 재작성본**을 포함한다. 이 재작성본이 발표의 "보완점" 섹션을 그대로 채운다. 프롬프트 해시를 키로 결과를 캐싱해 재실행 시 이미 채점한 것은 건너뛴다.

## 리포트 구성

HTML과 Markdown을 동시에 생성하며, 점수 원본은 `scores.json`으로 분리해 둔다. 리포트는 지표를 나열하는 대시보드가 아니라 **진단 → 해석 → 조언** 순서로 읽히는 한 편의 서사여야 한다. 그래프로 현재 상태를 먼저 보여 주고, 그 그래프에서 무엇이 읽히는지 말로 풀고, 마지막에 다음 주부터 뭘 바꿀지 알려 주는 흐름이다.

### 1부 — 진단 (그래프)

차트는 matplotlib으로 PNG를 만들어 HTML에 base64로 임베드하는 동시에 `out\charts\*.png`로도 남긴다. 발표 슬라이드에 그림을 그대로 옮겨 붙일 수 있어야 하기 때문이다. 색과 축 규칙은 dataviz 스킬을 따른다.

| 차트 | 내용 | 여기서 드러나는 것 |
| --- | --- | --- |
| 4분면 산점도 | 가로축 프롬프트 점수, 세로축 결과 점수, 점 1,718개 | 우리 프롬프트가 어느 구역에 몰려 있는가 |
| 길이 구간별 재작업률 | 프롬프트 길이 구간 대비 정정 발생 비율 막대 | 너무 짧아서 실패했나, 길어도 실패했나 |
| 도구 호출 분포 | Bash·Read·Edit·Write 등 가로 막대 | 읽지 않고 바로 고치는 습관이 있는가 |
| 주차별 추이 | 재작업률·중단률·도구 에러율의 시간 흐름 선 그래프 | 프로젝트가 진행되며 나아졌는가 |
| 안티패턴 빈도 | 모호어·범위 미지정·복수 요구 몰아넣기 등 발생 횟수 | 가장 자주 저지른 실수가 무엇인가 |
| 블라인드 대비 결과 인지 점수 | 두 채점의 점수 차 분포 | 우리가 좋다고 착각한 프롬프트가 얼마나 되나 |

각 차트 아래에는 그 차트가 말하는 바를 한 문장으로 붙인다. 그래프만 던져 놓지 않는다.

### 2부 — 해석 (잘한 점과 문제점)

수치에서 곧바로 결론으로 건너뛰지 않고, 각 주장마다 실제 프롬프트 원문과 그 직후에 벌어진 일을 근거로 붙인다.

- **잘한 점** — 상위 구역에서 반복되는 패턴 다섯 개. 각각 실제 프롬프트 인용, 그때 모델이 한 행동, 결과 점수를 함께 보여 준다.
- **문제점** — 안티패턴 다섯 개. 프롬프트 원문, 그 뒤 몇 턴을 더 썼는지, 중단이나 에러가 났는지, 최종적으로 커밋까지 갔는지를 이어서 보여 준다.
- **착각 구간** — 블라인드 채점은 높았는데 결과 점수가 낮았던 사례. 문장이 정돈돼 있다고 좋은 프롬프트가 아니라는 근거가 된다.

### 3부 — 조언 (다음에 뭘 바꿀 것인가)

조언은 매번 같은 일반론이 나오면 안 되고 이번 데이터에 반응해야 한다. 지표별 임계값을 걸어 두고, 넘긴 항목에 대응하는 조언 카드만 발동시킨 뒤 문장만 LLM이 다듬는 구조로 만든다. 예를 들어 재작업률이 기준치를 넘으면 "요구를 쪼개서 던지라"는 카드가, 도구 에러율이 높으면 "실행 전 상태 확인을 프롬프트에 포함하라"는 카드가 뜬다.

조언은 세 종류로 낸다.

| 종류 | 형태 |
| --- | --- |
| 우선순위 실행 항목 | 효과가 큰 순으로 3~5개, 각각 근거 지표를 달고 |
| before/after 재작성 | 실제로 실패했던 프롬프트 3건을 고쳐 쓴 예시 |
| 팀 규칙 제안 | 반복 지적을 CLAUDE.md에 넣을 규칙 문장으로 승격 |

**발행 전 마스킹 필수** — 프롬프트 원문에 DB 접속 정보, JWT 시크릿, 내부 IP가 섞여 있을 수 있다. 리포트에 원문을 인용하기 전에 정규식 마스킹을 거치고, 마스킹 통과 여부를 리포트 상단에 표시한다.

## 검증

1. 골든 세션 한 개를 손으로 라벨링해 두고, 도구가 뽑은 재작업·중단·결과 성공 판정과 대조한다. 불일치가 나오면 정정어 사전과 결과 점수 가중치를 조정한다.
2. git 대조 검증 — 커밋이 확실히 남은 세션(예: Backend-review 브랜치 작업) 하나를 골라 지속성 점수가 실제 커밋 이력과 맞는지 확인한다.
3. `python -m promptaudit --project reviewticket --no-llm`으로 지표·결과 단계까지 두 번 돌려 동일 출력이 나오는지 확인한다.
4. 마스킹 테스트 — 가짜 시크릿을 넣은 픽스처로 마스킹이 걸리는지 검사한다.
5. 최종 리포트를 브라우저로 열어 라이트/다크 양쪽 렌더링을 확인한다.
