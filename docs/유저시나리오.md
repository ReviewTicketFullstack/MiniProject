# 유저 시나리오

## 사용자 정의

| 구분 | 설명 |
| --- | --- |
| 주 사용자 | 클로드 코드로 실제 개발을 진행한 팀원 |
| 사전 조건 | 해당 PC에 세션 기록이 남아 있고, 분석 대상 프로젝트를 한동안 진행했다 |
| 사용 시점 | 주간 회고, 스프린트 종료, 발표 준비 |

---

## 시나리오 1 - 주간 회고에서 내 협업 습관을 확인한다

**상황** 한 주 동안 백엔드 API를 붙였고, 체감상 클로드에게 같은 일을 여러 번
다시 시킨 것 같다. 그런데 정확히 얼마나 그랬는지는 모른다.

**흐름**

1. 사용자가 클로드 코드에서 `/prompt-audit`을 입력한다.
2. 시스템이 세션을 선별하고 프롬프트별 지표를 계산한다. 몇 초 안에 끝난다.
3. 리포트가 열린다. 1부 첫 그림에서 자기 프롬프트가 네 구역 중 어디에
   몰려 있는지 바로 보인다.
4. 요약 카드에서 재작업률을 확인한다. 열 번에 한 번꼴로 정정이 붙었다는 사실을
   숫자로 처음 알게 된다.
5. 2부 문제점 항목에서 실제로 자기가 썼던 프롬프트 원문과, 그 뒤에 몇 턴이
   더 들었는지를 나란히 본다.

**결과** 인상이 아니라 수치로 자기 습관을 확인한다. 다음 주에 무엇을 바꿀지
3부 조언에서 우선순위대로 받는다.

---

## 시나리오 2 - 문장은 멀쩡했는데 결과가 나빴던 경우를 찾는다

**상황** 프롬프트를 꽤 신경 써서 길게 쓰는 편인데도 작업이 매끄럽지 않다는
느낌이 든다. 무엇이 문제인지 짚이지 않는다.

**흐름**

1. 1차 실행으로 리포트를 만든다. 이때 채점 대기열이 함께 만들어진다.
2. 클로드가 대기열을 읽고 각 프롬프트를 두 번 채점한다. 먼저 문장만 보고
   매기고, 그다음 실제로 벌어진 일까지 보고 다시 매긴다.
3. 채점 결과를 반영해 리포트를 다시 만든다.
4. "착각 구간" 항목에 문장 점수는 높았는데 결과 점수가 낮았던 프롬프트가
   모여 나온다.
5. 각 사례마다 무엇이 문제였는지 한 문장 판정과, 같은 의도를 더 잘 전달하는
   재작성본이 붙는다.

**결과** "더 자세히 쓰기"가 답이 아니라는 것을 확인한다. 길게 쓰는 것과 범위를
못 박는 것이 다른 일이라는 사실이 사례로 드러난다.

---

## 시나리오 3 - 발표 자료를 만든다

**상황** 금요일 발표에서 팀의 프롬프트 사용을 분석해 보여 줘야 한다. 슬라이드에
넣을 그림과 근거가 필요하다.

**흐름**

1. 리포트를 생성한다.
2. `out/charts/` 폴더에서 PNG 여섯 장을 꺼내 슬라이드에 붙인다. 발표 판형에
   맞춰 라이트 배경으로 고정되어 있다.
3. 2부 해석에서 잘한 점과 문제점 사례를 그대로 인용한다. 인용문은 이미
   마스킹을 거친 상태라 접속 정보나 토큰이 노출되지 않는다.
4. 3부 조언을 "보완점" 슬라이드로 옮긴다.
5. 발표 중 시연으로 명령을 한 번 더 실행해 같은 수치가 재현되는 것을 보여 준다.

**결과** 필수 발표 항목 네 가지(프롬프트 분석, 잘못된 점, 잘 사용한 점,
보완점)가 리포트 구조와 그대로 대응되므로 슬라이드 구성이 바로 나온다.

---

## 예외 흐름

| 상황 | 시스템 동작 |
| --- | --- |
| 채점을 하지 않은 상태 | 규칙 지표만으로 리포트를 완성한다. 착각 구간은 문장 점수와 결과 점수의 차로 대신한다 |
| 선별된 세션이 없음 | 프로젝트 이름을 확인하라는 메시지를 내고 종료한다 |
| 프로젝트 저장소가 없음 | 지속성 점수를 중립값으로 두고 나머지 세 층으로 결과 점수를 낸다 |
| 프롬프트에 비밀값 포함 | 인용 전에 마스킹하고, 어떤 규칙이 걸렸는지 리포트 말미에 밝힌다 |
| 이미 채점한 프롬프트 | 캐시에 있으므로 다시 묻지 않는다 |
