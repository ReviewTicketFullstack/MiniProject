# 유저 시나리오

이 문서는 사용자가 도구와 어떻게 상호작용하는지를 기술한다.

## 공통 전제

- 대상 저장소는 Git 저장소이며 빌드·테스트 명령이 정의되어 있다.
- 모든 Change Drill은 독립 Worktree에서 실행되며, 원래 작업 트리와 브랜치는 변경되지 않는다.
- 실험 결과는 병합 대상이 아니라 **관측 대상**이다. 실행이 끝나면 코드 변경분은 폐기되고 증거만 남는다.

---

## S1. 개발자가 수동으로 변경 실험을 시작한다

| 항목          | 내용                                        |
| ------------- | ------------------------------------------- |
| **Actor**     | 리팩터링 우선순위를 정하려는 개발자         |
| **선행 조건** | 저장소가 clean 상태, 시나리오 카탈로그 존재 |
| **트리거**    | `/change-drill` 실행                        |

**주 흐름**

1. 개발자가 `/change-drill`을 실행한다.
2. 시스템이 시나리오 카탈로그를 보여준다. 개발자는 하나를 고르거나 직접 문장으로 입력한다 (예: "Order에 cancellationReason을 추가하라").
3. 시스템이 실행 계획(시나리오, 기준 커밋, 검증 명령)을 요약해 보여주고 확인을 받는다.
4. 개발자가 승인하면 실험이 시작되고, 진행 상황이 단계별로 표시된다.

**Agent 동작** — Scenario Agent가 입력 문장을 실행 가능한 과제로 구체화(범위·완료 조건 명시)한다. Coding Agent가 격리된 Worktree 안에서 실제 개발자처럼 코드를 탐색·수정한다. Verification Agent가 빌드·테스트를 돌려 변경이 실제로 동작하는지 확인한다. Measurement Agent가 diff와 작업 로그에서 증거를 수집한다.

**시스템 동작** — 기준 커밋을 고정하고 Worktree를 생성한다. Coding Agent의 쓰기 범위를 해당 Worktree로 제한한다. 종료 후 diff와 증거를 보관하고 Worktree를 정리한다.

**출력** — 시나리오, 완료 여부, 변경 파일/함수/타입 수, 빌드·테스트 결과, 관측 서술, 해석이 담긴 리포트.

**예외 / 실패**

- 작업 트리에 커밋되지 않은 변경이 있음 → 기준 커밋이 모호하므로 실행 전 경고하고 중단
- Agent가 과제를 완료하지 못함 → **실패가 아니라 결과의 한 종류.** "미완료" 자체를 증거로 기록하고, 어디서 막혔는지 남긴다
- 빌드·테스트 명령을 찾지 못함 → 검증 없이 진행할지 사용자에게 확인
- 시나리오가 모호해 Agent가 임의로 범위를 넓힘 → 관측 항목으로 기록

**사용자 가치** — 실제로 코드를 건드리기 전에, 그 변경이 어디까지 번지는지 미리 본다.

## S2. 개발자가 여러 시나리오를 병렬로 실행한다

| 항목          | 내용                                               |
| ------------- | -------------------------------------------------- |
| **Actor**     | 코드베이스의 취약 축을 파악하려는 테크리드         |
| **선행 조건** | 시나리오 3개 이상 선택 가능, 디스크·실행 예산 여유 |
| **트리거**    | `/change-drill`에서 복수 시나리오 선택             |

**주 흐름**

1. 개발자가 서로 다른 성격의 시나리오를 여러 개 선택한다 (도메인 필드 추가 / 인증 방식 교체 / 문구 일괄 변경).
2. 시스템이 총 실행 규모와 예상 비용을 알리고 확인을 받는다.
3. 각 시나리오가 **동일한 기준 커밋**에서 출발해 동시에 실행된다.
4. 개발자는 진행 현황판에서 각 실험의 상태를 본다.

**Agent 동작** — 시나리오마다 독립된 Agent 집합이 붙는다. 서로의 Worktree나 중간 결과를 참조하지 않는다. 한 Agent의 실패가 다른 실험에 전파되지 않는다.

**시스템 동작** — 시나리오 수만큼 Worktree를 만들고 실행 경계를 격리한다. 동시 실행 수에 상한을 둔다. 모든 실험이 끝나면 결과를 한 실행 단위로 묶는다.

**출력** — 시나리오별 개별 리포트 + 실행 단위 요약.

**예외 / 실패**

- 한 실험만 실패 → 나머지는 그대로 진행하고, 요약에 해당 실험을 "미완료"로 표시
- Worktree 생성 실패 / 디스크 부족 → 실행 가능한 수만큼만 시작하고 나머지는 대기
- 병렬 실행 부하로 테스트가 간헐 실패 → 검증 결과 신뢰도를 낮게 표시하고 재검증 제안
- 시나리오끼리 사실상 같은 코드 영역을 건드림 → 독립성이 낮다고 표기 (비교 시 주의)

**사용자 가치** — 변경 유형별로 코드베이스의 반응을 나란히 놓고 본다. 격리는 성능이 아니라 **실험의 타당성**을 위한 것이다.

## S3. 개발자가 실험 결과를 확인한다

| 항목          | 내용                                    |
| ------------- | --------------------------------------- |
| **Actor**     | 실험을 요청한 개발자                    |
| **선행 조건** | 완료된 Change Drill 1건 이상            |
| **트리거**    | 실행 완료 알림, 또는 저장된 리포트 열람 |

**주 흐름**

1. 개발자가 리포트를 연다.
2. 결과 → 변경 비용 → 관측 → 해석 순으로 읽는다.
3. 숫자가 납득되지 않으면 실제 diff를 펼쳐 확인한다.
4. 필요하면 같은 시나리오를 재실행한다.

**Agent 동작** — Analysis Agent가 수치를 문장으로 옮긴다. "8개 파일이 바뀌었으므로 나쁘다"가 아니라 "변경이 도메인 타입 → API 매핑 → 상태 관리 → UI로 전파되었다"처럼 **경로**를 서술한다.

**시스템 동작** — 원시 증거와 해석을 분리해 보여준다. 해석에는 근거가 된 증거 항목이 연결된다.

**출력** — 실행 결과, 변경 비용, 빌드·테스트 상태, 관측 서술, 맥락적 해석, 전체 diff.

**예외 / 실패**

- 해석이 품질 판정처럼 읽힘 → 문구 규칙 위반으로 간주하고 교정 대상
- 증거는 있는데 해석이 근거를 넘어섬 → 해석 대신 "판단 보류" 표기
- 테스트는 통과했지만 요구한 변경이 실제로 이뤄지지 않음 → **가장 위험한 케이스.** 완료 여부는 테스트 통과와 별도로 판정하고 불확실하면 그렇게 표시

**사용자 가치** — 결론이 아니라 근거를 받는다. 동의하지 않을 자유가 남는다.

## S4. 개발자가 시나리오 간 변경 비용을 비교한다

| 항목          | 내용                                    |
| ------------- | --------------------------------------- |
| **Actor**     | 아키텍처 개선 항목을 고르려는 테크리드  |
| **선행 조건** | 같은 기준 커밋에서 실행된 실험 2건 이상 |
| **트리거**    | 실행 단위 요약 열람 또는 비교 요청      |

**주 흐름**

1. 개발자가 비교할 실험들을 고른다.
2. 시스템이 시나리오별 비용을 나란히 보여준다.
3. 개발자가 편차가 큰 항목을 짚는다 (예: 필드 추가는 3파일, 인증 교체는 21파일).
4. 개발자가 어느 축을 먼저 손볼지 판단한다.

**Agent 동작** — Analysis Agent가 축 단위로 대비를 서술한다. 시나리오들을 **하나의 종합 점수로 합산하지 않는다.**

**시스템 동작** — 기준 커밋이 다르거나 검증 조건이 다른 실험은 비교 대상에서 제외하거나 경고를 붙인다.

**출력** — 비교 표, 편차가 큰 축, 축별 서술.

**예외 / 실패**

- 기준 커밋이 다름 → 비교 불가로 표시
- 시나리오 난이도 자체가 달라 비교가 부당함 → 규모 차이를 명시하고 직접 비교를 만류
- 실험 회차마다 결과가 크게 흔들림 → 단일 실행 결과로 결론 내지 말라고 경고
- 사용자가 순위표를 요구함 → 순위 대신 축별 대비로 제공

**사용자 가치** — "무엇부터 고칠까"에 대해 직관이 아닌 관측을 근거로 삼는다.

## S5. 개발자가 자동 Hook으로부터 결과를 받는다

| 항목          | 내용                                              |
| ------------- | ------------------------------------------------- |
| **Actor**     | 평소 작업 중인 개발자 (실험을 직접 요청하지 않음) |
| **선행 조건** | 자동 실행이 켜져 있고 대상 시나리오가 지정됨      |
| **트리거**    | 작업 종료 시점, 정기 실행, 또는 저장소 변경 감지  |

**주 흐름**

1. 개발자가 평소처럼 작업한다.
2. 정해진 조건이 충족되면 실험이 배경에서 실행된다.
3. 완료 시 요약이 도착한다. 이전 실행 대비 변화가 있으면 그 점이 강조된다.
4. 개발자는 무시하거나, 상세 리포트를 연다.

**Agent 동작** — 사용자의 현재 작업을 방해하지 않는다. 결과는 알림일 뿐 승인 요청이 아니다.

**시스템 동작** — 실행 조건과 빈도에 상한을 둔다. 변화가 없으면 조용히 넘어간다.

**출력** — 짧은 요약 알림 + 전체 리포트 링크.

**예외 / 실패**

- 알림이 잦아 소음이 됨 → **채택을 가장 크게 위협하는 실패 모드.** 변화가 있을 때만 알린다
- 저장소가 불안정한 상태에서 실행됨 → 실행을 건너뛴다
- 배경 실행이 사용자 작업과 자원 경합 → 우선순위를 낮추고 필요하면 연기
- 결과가 성과 지표처럼 소비됨 → 개인·팀 평가 용도가 아님을 리포트에 명시

**사용자 가치** — 변경 비용의 추세를 요청하지 않고도 알게 된다.

## S6. 개발자가 비용이 높게 나온 변경을 파고든다

| 항목          | 내용                           |
| ------------- | ------------------------------ |
| **Actor**     | 예상보다 높은 비용을 본 개발자 |
| **선행 조건** | 파급 범위가 넓게 나온 실험 1건 |
| **트리거**    | 리포트에서 해당 실험을 선택    |

**주 흐름**

1. 개발자가 "왜 21개 파일이 바뀌었는가"를 묻는다.
2. 시스템이 변경을 계층·모듈 단위로 묶어 전파 경로를 보여준다.
3. 개발자가 Agent의 작업 과정을 되짚는다 — 어디서 헤맸는지, 무엇이 모호했는지, 어떤 파일을 반복해 찾았는지.
4. 개발자가 원인을 판단한다: 구조 문제인가, 도메인 본질의 복잡도인가, 아니면 Agent의 한계인가.
5. 필요하면 조건을 바꿔 재실험한다.

**Agent 동작** — Analysis Agent가 전파 경로를 제시하되 **원인을 단정하지 않는다.** 가능한 해석을 복수로 제시하고 판단은 사용자에게 남긴다.

**시스템 동작** — 변경 파일을 계층/모듈로 묶고, 요구된 변경과 직접 관련 없는 수정은 따로 표시한다. 재실험 시 이전 실행과 나란히 놓는다.

**출력** — 전파 경로, 계층·모듈별 변경 분포, 무관 수정 목록, Agent가 겪은 모호함 기록, 복수 해석.

**예외 / 실패**

- 높은 비용의 원인이 Agent 능력 한계임 → **이 프로젝트의 최대 리스크.** 코드베이스 특성과 구분되지 않으면 그 사실 자체를 명시한다
- 계층 구분이 정의되지 않은 저장소 → 계층 기준 분석을 생략하고 모듈 단위로만 제공
- 무관 수정이 실은 필요한 변경이었음 → "무관"이 아니라 "직접 관련성 낮음"으로 표기
- 재실험 결과가 크게 다름 → 비결정성을 관측 결과로 함께 기록

**사용자 가치** — 숫자에서 멈추지 않고, 그 비용이 어디서 왔는지까지 도달한다.

---

## 시나리오 전반의 설계 원칙

1. **모든 출력은 증거 → 해석 순서.** 해석은 증거 없이 존재할 수 없다.
2. **미완료도 결과다.** Agent가 실패한 실험을 버리지 않는다.
3. **점수화하지 않는다.** 단일 종합 점수는 이 도구를 코드 리뷰 도구로 되돌린다.
4. **불확실성을 감추지 않는다.** 신뢰도가 낮은 관측은 낮다고 표시한다.
5. **평가 도구가 아니다.** 개인·팀 성과 측정 용도가 아님을 산출물에 명시한다.
