# 유저 시나리오

## 공통 전제

- 대상은 Git 저장소다.
- 원본 저장소는 변경되지 않는다. 예측 모드는 읽기만, 구현 모드는 Worktree만 건드린다.
- 실험 결과는 병합 대상이 아니라 **관측 대상**이다. 코드 변경분은 폐기되고 증거만 남는다.

---

## S1. 변경 비용을 미리 예측한다 🟢

| 항목       | 내용                                    |
| ---------- | --------------------------------------- |
| **Actor**  | 착수 전에 변경 규모를 가늠하려는 개발자 |
| **트리거** | `/change-drill` 실행                    |

**흐름**

1. 저장소 경로를 묻는다 (기본: 현재 디렉터리).
2. **"어떤 변경을 예측할까요?"** — 자연어로 자유롭게 입력한다. ✅
3. 어시스턴트가 임시 시나리오(id/name/description/prompt)를 만들어 확인받는다.
4. `--predict`로 저장소를 검증한다. Worktree는 만들지 않는다.
5. 읽기 전용 Agent 2개가 병렬로 코드를 분석하고 각자 예측 JSON을 저장한다.
6. `--predict-report`가 두 예측을 집계해 터미널 리포트를 출력한다.
7. `git status`로 저장소가 그대로인지 확인한다.

**출력** — 고정된 순서의 터미널 리포트:
KEY METRICS(토큰/파일 수/LOC/복잡도, Agent A·B 나란히) → 막대 그래프 →
CONSENSUS(합치도) → DIFFERENCE(차이) → 추정치 고지.

> 모든 수치는 **정적 분석 기반 추정치**다. 실측값이 아니며 실제 구현 비용을 보장하지 않는다.
> 상세 관찰(구현 접근, 결합도, 중복, 책임, 변경용이성)은 터미널에 표시되지 않고 JSON에만 남는다.

## S2. 실제로 변경을 수행해 비용을 측정한다 🟡

| 항목          | 내용                                             |
| ------------- | ------------------------------------------------ |
| **Actor**     | 리팩터링 우선순위를 정하려는 개발자              |
| **선행 조건** | `scenarios.json`에 시나리오가 정의되어 있어야 함 |

**흐름**

1. 시나리오 카탈로그에서 하나를 고른다. ✅
   - 🔴 구현 모드는 자유 입력 미지원. 카탈로그 ID 또는 `--scenario-json`만 받는다.
2. `--phase setup`이 기준 커밋을 고정하고 Worktree를 만든다. ✅
3. Coding Agent가 Worktree 안에서 실제로 코드를 수정한다. ✅
   - 🟡 쓰기 범위 제한은 프롬프트 지시일 뿐, 파일시스템 샌드박스는 없다.
4. `--phase measure`가 diff를 파싱하고 빌드를 실행한 뒤 Worktree를 정리한다. ✅

> 🔴 **Agent는 Coding Agent 하나뿐이다.** Scenario / Verification / Measurement Agent는
> Agent가 아니라 `src/` 안의 Python 함수다.
> 🔴 `--phase full`은 Agent를 기다리지 않아 빈 diff를 측정한다. 실험에 쓰지 않는다.
